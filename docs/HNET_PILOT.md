# LightNest × H-Net：动态分块完整 ELF 生成实验

本质上，这是让模型学习“哪些时刻值得更新中间层状态”，而不是每个字节都做同样多的中间层计算。

## 结论

已完成可选模块接入与四组、三个种子的实际 CPU 训练。动态分块成功把中间序列缩短到平均约四分之一，但没有建立稳定的生成能力优势：三个种子的完整生成分别为 **29/64、0/64、0/64**。第一种子有正面结果，另外两个未复现；不压缩的同参数量分层对照平均成功率更高。保留为实验模块，不替换现有默认生成器。

所有模型的成功样本都只来自退出码程序；每个模型、每个种子的八字节 stdout 任务都是 **0/32**。这不是复杂 ELF、任意程序生成或 RSI 成功的证据。

给定正确前缀时，动态分块 BPB 比固定分块高约 80.4%，而不是更低。其自由生成变量字节准确率为 7.87%，原模型为 9.26%，固定分块为 25.93%，不压缩分层模型为 25.46%。这些指标共同说明，动态组的局部完整成功并不意味着已经学会可靠生成请求相关内容。

## 失败与路由检查

动态组种子 11 的退出码测试有 29/32 完整成功，但请求 exit=156 提前在 197 字节停止，目标为 400 字节。种子 23 的所有退出码请求都失败，部分文件的第一处错误在偏移 62；种子 37 的退出码文件第一处错误都在偏移 2。因此不能把失败仅归结为输出载荷复制；早期结构字节、误差累积和停止判断都需要排查。这里只描述观察，不把这些现象冒充已证实的因果解释。

路由确实不是每四字节的固定规则：同一模型的 stdout 测试请求之间，有 61、107、101 个位置分别在三个种子中出现不同边界。但边界同时受请求和绝对位置影响，尚未与指令或语义边界标签比较，不能称为“自动发现 x86 指令语义”。路由诊断是测试完成后的描述性分析，没有用于选模。

## 机制与接入边界

本质上，动态分块是在逐字节网络中加入一个可训练的开关：开关打开时才更新中间层状态，其他时刻沿用最近的中间层信息。它改变的是模型内部计算的粒度，不是让生成器借助编译器输出程序。

新模块 `lightnest/hnet.py` 的 `HNetELFGenerator` 继承现有 `ELFGenerator`，仅替换 `decode`。原有请求条件、复制头、蓝区位预测、红区迭代与停止头不变；旧类、旧默认行为与旧检查点格式没有改动。新实验从随机初始化训练，不是给现有已训练权重打补丁。本次没有更改 GreenObserver、Any2Any 主干、强化学习或模型自修改流程。

内部数据流为：字节与请求 → 因果 GRU 编码 → 学习边界 → 取出边界处的状态 → 较短序列上的 GRU → 平滑并展开 → 字节级 GRU → 现有 RGB 输出头。实现保留 H-Net 的相邻状态余弦路由、硬边界选择、指数平滑、直通梯度以及目标分块率损失 [1, §2.2]。最小表达式是：

```text
h[t] = encoder(previous_byte, request, h[t-1])
p[t] = (1 - cosine(Wq*h[t], Wk*h[t-1])) / 2
boundary[t] = (p[t] >= 0.5)       # 序列开头强制打开
if boundary[t]:
    main_state = main(h[t], main_state)
    smooth = p[t]*normalize(main_state) + (1-p[t])*smooth
output[t] = decoder(skip(h[t]) + smooth)
```

实际训练还对路由置信度使用直通梯度，并加上权重 0.03 的分块率损失；伪代码省略了批处理、掩码、红区和输出头。这里只选择当前边界的因果编码状态，不平均尚未出现的后续字节，避免训练时偷看未来。批量训练和逐字节生成都保存编码器、中间层、解码器、上一键向量与平滑状态。

这不是原论文大模型的复现。为了在当前 CPU 环境做机制对照，三个阶段都用 GRU，只有一层分块；没有原论文的 Mamba-2 外层、多层递归层级、学习率调制或大规模训练。查询/键矩阵采用独立随机初始化，而不是官方实现的单位矩阵初始化。原论文强调把主要容量放到压缩后的主网络 [1, §2.1]；本试验各阶段同宽且中间层很小，因此不能用它直接检验原论文的规模化效率结论。

## 冻结实验协议

运行前写入 `protocol.json`，所有十二次训练结束后才运行测试集；这是本地冻结协议，不是第三方登记的预注册。四组对照分别是现有两层 GRU、三阶段但不压缩的 dense、每四个位置取一个状态的 fixed，以及学习边界的 dynamic。后三组的参数张量、初始化和配置相同；fixed/dense 的路由参数不参与任务计算，因此“参数数目相同”不代表每一项参数都有效使用。原模型有 58,290 个参数，三阶段模型各有 67,890 个参数，后者多约 16.5%，不能把相对原模型的任何变化全归因于路由。

训练集 320、验证集 48、测试集 64。参考数据来自与仓库 `corpus.py` 相同的 GNU 汇编/链接构建方式 [2]：256 个指定退出码程序，以及 176 个输出指定八字节的程序。训练分别使用 192/128 个，验证 32/16 个，测试 32/32 个。文件长度为 400 或 504 字节。全部 432 个已知参考程序都经过实际执行，退出码与输出符合请求。三个划分没有完整文件哈希重叠，但它们来自相同的两个程序骨架：这是未见请求值测试，不是未见算法、编译器、布局或大型程序测试。

训练设置为宽度 32、输出容量 640 字节、批量 8、每组 300 次更新、AdamW 学习率 0.003、权重衰减 0.01、梯度裁剪 1、红区深度 2。随机种子为 11、23、37。同一种子的四组使用完全相同的采样顺序，保存批次表供复核。比较匹配数据和更新次数，但不匹配浮点运算量或耗时。模型仅依据验证集的原始 `generation_loss` 选取检查点，选择标准不含分块率辅助损失。运行顺序按种子轮换；仍不能将单次 CPU 计时视为严格性能基准。

主指标是无教师辅助的完整文件逐字节一致，并由模型在正确位置停止。模型从 BOS 开始自行生成，没有拼接文件头、提供目标长度、套模板、编译或事后修复。次指标包括给定正确前缀时的每字节负对数似然（BPB，越低越好）、完整字节准确率、变量字节准确率、分块比例和计时。BPB 对每个字节的八个位损失求和后除以 ln(2)，不是每位损失冒充每字节损失。变量位置仅由训练集发现：退出码族是偏移 177，stdout 族是偏移 209–216。

“给定正确前缀”评估的是下一字节预测，不是完整生成成功率。固定字段占比很大，整体准确率可能掩盖请求相关内容的错误。本报告同时提供变量字段指标，但不同任务族的变量字节数量不同；总体变量准确率按字节加权，分族结果在原始记录中单列。

## 复核、限制与复现

动态组和固定组的差异是一整套动态路由训练机制，包括可变边界、平滑、直通梯度和辅助损失；本轮没有逐一消融这些成分。因此负面结果不能定位到其中某一个设计，也不意味着原论文 H-Net 在其训练条件下无效。三个随机种子仅用于观察波动，不足以给出强统计推断；没有使用显著性或规模化能力结论。

机制和评估共 17 项单元测试通过，覆盖因果前缀不变性、整段与流式推理一致性、无边界时跳过中间层、EMA 数值与梯度、路由器任务梯度、参数对照、BOS/目标移位、批量生成一致性和 BPB 单位。独立复核脚本检查固定源码哈希、参考文件哈希、划分、批次顺序、验证集选模，并从落盘生成文件和逐样本记录重新计算结果。

当前执行环境为 Python 3.13.5、PyTorch 2.10.0+cpu、两个计算线程、无 CUDA、GNU binutils 2.44；仓库锁定环境是 PyTorch 2.12.1。这里的数字是实际当前环境的结果，不应冒充锁定环境复现。当前工作区是经 Git 对象哈希核对的局部源码快照，不是完整仓库克隆。由于缺少 bubblewrap 和 llvm-mc，没有运行全仓库 `tools/check.py`，也没有验证 Lean 证明。

未知的生成文件没有被直接执行。只有逐字节完全等于已验证参考文件、且正确停止时，才记录“由精确身份确认行为”。不完全一致的文件可能行为正确，也可能完全无效；本实验没有把这两类情况区分开。ELF 魔数正确只代表前四字节吻合，不代表合法 ELF 或能执行。
