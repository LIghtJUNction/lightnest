# Qwenputer P0：本地 CPU 验证

日期：2026-10-29 UTC。代码基线：`b457347b3e7b3cd9a6fbcefab34e99927e103025`。
这是新运行的机制验证，不是模型晋升，也没有训练或生成 ELF。

## 实际做了什么

保留原 P0 的 `ExactBitRAM`、`FixedWordAdder` 和基础探针；新增多种子压力脚本与三项测试。
没有修改 RGB 模型、训练入口、隔离执行器、依赖或历史归档。
原始日志、JSON 与数据留在源码仓库外，仓库仅提交源码、测试和本报告。

环境：Python 3.13.5、PyTorch 2.10.0+cpu、
NumPy 2.3.5、Linux x86-64、CPU、单 Torch 线程；没有 CUDA。
使用本机已有 Python 环境，未执行 `uv sync --locked`，不声称完整锁定环境复现。
直接 git clone 因 DNS 不通失败；测试使用补丁源码和 GitHub 接口读取且核对 blob 的必要基线文件。
这是局部源码工作区，不是已克隆的完整仓库。

新增测试验证尾批次、跨 dtype 相同输入和相同结果，以及故意破坏输出后能检测到持续错误。

## 闭环到底验证了什么

每个通道有独立 RAM 和进位。宿主按冻结顺序循环选择 8 行，生成种子确定的外部增量。
读取出的位、固定加法器输出和进位直接进入后续步骤；整数参考只观察，不写回修复状态。
每次检查读取值、结果、进位，结束后检查全部内存。FP32/BF16 输入摘要及最终整数摘要相同。

负对照把加法器的结果位翻转。测试确实观察到错误结果、后续读错和最终内存差异，
表明该探针没有把正确参考偷偷覆盖回去。它不能证明任意规模或所有后端都正确。
地址调度和循环仍由宿主提供；这不是完整指令执行、模型自主规划或自由运行 CPU。

## 复现

完整仓库及所需编译/沙箱依赖就绪后，从仓库根目录运行：

```bash
uv sync --locked
uv run --locked python -m unittest discover -s tests -p 'test_rgb_exact_core.py' -v
PYTHONPATH=. uv run --locked python archive/research/tools/stress_exact_core.py \
  --ram-steps 100000 --addition-cases 131072 --feedback-steps 2048 \
  --seeds 20261029 20261030 20261031 > ../lightnest-p0-stress.json
uv run --locked python tools/check.py
```

本机实际使用等价的 `PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=. python ...`，不使用 uv 锁定环境。
任何比较不一致时压力脚本输出 JSON 并以非零码退出。源码哈希、输入摘要和版本包含在 JSON 中。
时间戳和耗时不要求逐字复现，输入与数值结果应一致。
