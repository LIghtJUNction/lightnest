> [!IMPORTANT]
> LightNest is an active research repository. It does **not** currently demonstrate arbitrary binary understanding, arbitrary program generation, complete ISA coverage, or safe execution of unknown code.

## Real-world internal execution research

A new experimental model proposes complete **Linux x86-64 ELF bytes** and evaluates a small subset of real x86 instructions using tensor operations within its forward pass. It also includes a limited learned Linux `openat` predictor and two real PTX integer operations. It does not define a custom ISA or embed a system image. This is a research prototype with incomplete CPU, GPU and operating-system coverage, not a full virtual machine.

In a tiny GPU experiment using one ELF skeleton, 3 of 4 held-out combinations passed both the internal check and independent native execution; the trained second round did not improve on the first. The experiment accepts structured requests, not natural language, and is not connected to the Ollama commands below. Details, limitations and reproduction: [internal world experiment](docs/INTERNAL_WORLD.md).

## Natural-language commands

The `create`, `explain` and `edit` commands use a local Ollama model, independently of LightNest's experimental trained generator. Install and start Ollama, then download the default model once:

```bash
ollama pull qwen3:8b
```

```bash
# Write a complete ELF directly as model-generated bytes.
./lightnest.sh create "Print Hello World and exit" -o hello.elf

# Explain an ELF without executing it.
./lightnest.sh explain hello.elf

# Propose fixed-length byte patches and write a new file.
./lightnest.sh edit hello.elf "Change Hello to Hallo" -o hello-edited.elf
```

`-o` is optional: defaults are `generated.elf` and `<input>.edited`. Existing outputs are never overwritten. Select another local model with `--model NAME`; an Ollama service runs locally at `127.0.0.1:11434`. Generated and edited files are checked as ELF but are **not behaviorally verified**. For creation, invalid ELF responses can be retried up to three times using parser feedback. Models can still return incorrect bytes, make invalid edits, or fail the request. Explanation uses ELF metadata, entry-point disassembly and a bounded selection of file bytes; it is not proof of program behavior. The model input limit for editing is 4096 bytes; explanation supports files up to 16 MiB. The editing mode only supports fixed-length changes to x86-64 ELF files.

## What the project is actually testing

The current mainline gives a model the **complete bytes of an ELF executable**, not only a disassembled function, then measures four separate capabilities:

```text
inspect structure and behavior
             ↓
propose a bounded byte edit
             ↓
execute the candidate in isolation
             ↓
learn from visible outcomes

or

generate every byte of a complete executable image
```

Deterministic tools parse ELF headers, segments, sections, entry points, dependencies and imports. Those parser results are recorded separately from anything the model learns. A parser correctly locating an entry point is not evidence that the neural model understands the program.

The generator must emit the complete file. The writer does not attach an ELF header, copy a template, invoke a compiler, or silently repair malformed output after generation.

## RGB in plain terms

RGB is a division of work, not three mysterious kinds of intelligence:

| Part | Simple responsibility |
| --- | --- |
| **Green** | Read repeated byte/log content once, keep every location, and build a compact evidence bank with routes back to original detail |
| **Blue** | Make a cheap first proposal and decide whether deeper computation is justified |
| **Red** | Reuse the same evidence and recurrent state for more reasoning steps, then stop or propose another action |
| **Notebook** | Keep a learned, content-addressed working set for long files instead of truncating only by position |

```text
complete file
    ↓
Green: compress global evidence + retain exact locations
    ↓
Blue: cheap candidate / STOP decision
    ↓ difficult case
Red: query the same evidence repeatedly
    ↓
edit, execute, observe, update state
```

A committed edit invalidates affected evidence before the next observation. Compute depth is trained from task utility rather than hard-coded file-size thresholds.

The attention design is informed by [Mixture-of-Top-k Attention](https://arxiv.org/html/2602.01219v6), especially its combination of compressed global information and routed original details. LightNest is a CPU-oriented adaptation for executable files, not a reproduction of the paper's vision training or throughput claims.

Full architecture and boundaries: [RGB design](docs/RGB_DESIGN.md).

## Current evidence

The current real-data curriculum contains:

| Material | Current scope |
| --- | ---: |
| Installed command-line programs | 16 |
| Complete ELF edit tasks | 2,048 |
| Complete ELF generation samples | 864 |
| Primary training architecture | Linux x86-64 |
| Any2Any input capacity | 1 MiB |
| Local attention window | 4,096 tokens |

Faults are artificially injected. The current generation curriculum asks for very small observable programs, such as a specified exit code or an eight-byte output. These are useful controlled tasks, not a claim that the model can generate general software.

Multi-architecture encode/decode interfaces reuse iced-x86 and LLVM, but actual model training and execution currently target x86-64.

## Milestones and limits

- The complete-image generator and isolated execution loop are implemented. A candidate must stop, pass ELF inspection and match the requested behavior before the `generate` command writes it.
- A small H-Net pilot compared four architectures on 64 unseen request values per run. Dynamic chunking produced exact, correctly stopped files for 29, 0 and 0 requests across three seeds; all successful samples were exit-code programs. All eight-byte output requests scored 0/32 across every architecture and seed. These tasks share simple program skeletons, and exact-file matching is stricter than behavioral equivalence. See [H-Net pilot](docs/HNET_PILOT.md).
- Earlier function-editing experiments combined neural proposals with visible-case verification and achieved 237/256 and 236/256 on two runs. These were limited synthetic-function tasks; the result includes the verifier, not just the neural model. See [historical results](docs/RESULTS.md).
- The standalone executable evaluator has run the published Prompt2ELF Hello World example against two simple cases. This verifies an existing sample, not generation by LightNest. See [benchmark notes](docs/BINARY_GENERATION_BENCHMARK.md).

The code-to-description alignment experiment below also records an important negative result.

## A negative result kept visible

The external code-to-description alignment experiment changed the objective from byte reconstruction to matching complete functions with their documentation. It also fixed a request encoder that previously lost word order.

The frozen validation result did **not** pass:

| Method | Top-1 | Top-5 |
| --- | ---: | ---: |
| Previous byte-reconstruction checkpoint | 2.73% | 4.69% |
| New learned alignment model | 10.74% | 22.46% |
| Lexical TF-IDF baseline | **49.41%** | **72.07%** |

Because the model remained far below the lexical baseline, the candidate was not promoted and the external test and LightNest blind-test sets were not queried. This prevents a failed validation result from being converted into a success claim by repeatedly checking held-out data.

The result proves only that the new objective improved over the previous checkpoint on this frozen validation set while still failing the acceptance threshold. It does not establish source-code semantics or binary behavior understanding.

Protocol, hashes, sampling limits and reproduction commands: [semantic alignment experiment](docs/SEMANTIC_ALIGNMENT.md).

## Artifact and execution boundary

Generated or edited files are written to new paths; source executables remain unchanged.

```text
candidate bytes
      ↓
ELF preflight
      ↓
bubblewrap namespaces
      ↓
no network + resource limits + process-creation filter
      ↓
typed result: pass / mismatch / invalid ELF / timeout / signal / isolation failure
```

The runner uses an isolated filesystem, no network, resource limits and a seccomp policy that denies process creation. Exact result caches bind the image hash, input, arguments and execution policy.

Isolation reduces risk; it does not mathematically prove arbitrary machine code safe. Tests passing on visible inputs also do not prove full program correctness.

## Editing loop

The editor receives only:

- the original file;
- the requested change;
- visible training or evaluation examples;
- typed execution feedback from visible cases.

It does not receive hidden-test results or clean target bytes as reward. Fixed-length patches include expected-image and expected-before-byte preconditions. Before/after hashes make the action replayable.

```pseudo
candidate = model(file, request, visible_evidence)
result = isolated_execute(candidate, visible_cases)
reward = new_passes - regressions - typed_failure_penalties
update(action_that_created_candidate, reward)
```

This is bounded reinforcement from an execution environment, not unrestricted self-modifying code.

## GPU generator training

The experimental LightNest generator can train on an NVIDIA GPU using a separate CUDA-enabled PyTorch environment. This does not train the Ollama model used above. `train-generator` defaults to CUDA and reports an error if CUDA is unavailable; use `--device cpu` explicitly with the locked CPU environment.

For an existing prepared corpus at `OUT`, create a separate environment and run:

```bash
GPU_ENV=/path/outside/checkout/lightnest-cuda-env
uv venv --python 3.13 "$GPU_ENV"
UV_HTTP_TIMEOUT=600 UV_CONCURRENT_DOWNLOADS=4 uv pip install \
  --python "$GPU_ENV/bin/python" --torch-backend cu130 \
  'torch==2.13.0' 'numpy==2.3.5' 'iced-x86==1.21.0' \
  'pyelftools==0.32' 'tokenizers==0.23.3'
"$GPU_ENV/bin/python" -m lightnest train-generator --out "$OUT" --device cuda
```

This environment is separate from the CPU lockfile; its CUDA dependencies are not locked by `uv.lock`. Training records its actual PyTorch version, CUDA version and GPU name. See [RGB reproduction](docs/RGB_REPRODUCE.md) for preparing the corpus, evaluation and resource requirements. The older policy and refinement training commands have not been moved to GPU; the separate internal-world experiments also support CUDA.

## Run the tools

Use Linux x86-64, Python 3.13 and [uv](https://docs.astral.sh/uv/). Dependencies are locked to PyTorch 2.13.0 CPU on Linux. Native execution additionally requires `bwrap` and libseccomp; training and the full checks require GCC, Clang, LLD, LLVM and the command-line programs used by the corpus. The runner needs working Linux user namespaces.

```bash
uv sync --locked
uv run --locked python -m lightnest --help
uv run --locked python tools/check.py
```

### Inspect and decode

```bash
# Print ELF metadata for an installed program.
uv run --locked python -m lightnest inspect /usr/bin/sort

# List supported LLVM targets and decode an x86-64 byte sequence.
uv run --locked python -m lightnest targets
uv run --locked python -m lightnest decode \
  --architecture x86_64 --hex 4889f84801f0c3
```

These commands use deterministic parsers and instruction decoders; they do not require trained weights.

### Evaluate an existing ELF

Create a temporary suite and test `/usr/bin/cat` with two byte inputs:

```bash
TASK_DIR=$(mktemp -d)
cat >"$TASK_DIR/cases.json" <<'EOF'
{
  "name": "cat-example",
  "cases": [
    {"input": {"args": [], "stdin": "610a"},
     "expected": {"returncode": 0, "stdout": "610a", "stderr": ""}},
    {"input": {"args": [], "stdin": "6200"},
     "expected": {"returncode": 0, "stdout": "6200", "stderr": ""}}
  ]
}
EOF
uv run --locked python tools/evaluate_binary.py \
  /usr/bin/cat "$TASK_DIR/cases.json"
```

`stdin`, `stdout` and `stderr` are hexadecimal bytes: `610a` means `a` followed by a newline. The JSON report includes the image and suite hashes, ELF metadata and each case's result. The command exits with status 0 only when every case passes. Remove the temporary directory when finished.

The execution policy denies networking and process creation, so it cannot evaluate a network server or programs needing subprocesses as functional successes. An isolation error is an infrastructure failure, not a program correctness result. See [benchmark notes](docs/BINARY_GENERATION_BENCHMARK.md).

### Generate an ELF with a trained checkpoint

The repository does not include trained weights. You need a compatible LightNest generator checkpoint, or must first prepare a corpus and train one using [RGB reproduction](docs/RGB_REPRODUCE.md). The current generator accepts either an exit status from 0 to 255 or **exactly eight bytes** of output encoded as hex; it does not accept arbitrary natural-language programming requests.

```bash
# Replace with an existing, compatible checkpoint outside the checkout.
CHECKPOINT=/path/to/generator.pt
TASK_DIR=$(mktemp -d)
printf '{"exit":37}\n' >"$TASK_DIR/request.json"

uv run --locked python -m lightnest generate \
  --checkpoint "$CHECKPOINT" \
  --request "$TASK_DIR/request.json" \
  --output "$TASK_DIR/generated.elf" \
  --workdir "$TASK_DIR/work"
```

An output request can instead contain `{"stdout":"68656c6c6f21210a"}`, meaning `hello!!` followed by a newline. The output path and work directory must be new and outside the checkout. The command checks that the model stopped, the ELF parses and its isolated execution matches the request; a failure does not publish an output file. These checks cover the specified behavior only. Generation is experimental and is not guaranteed to succeed.

For editing, frozen evaluation, and a complete training example, see [RGB reproduction](docs/RGB_REPRODUCE.md). Weights, original executables, caches, training logs and per-example results remain outside the repository.
